# 配置奖励与直接发放

奖励有两种输入，共用装备生成与现有发放记录：

- 配置奖励：怪物、宝箱、世界事件按来源节点查奖励池，计算触发概率和权重，得到模板、品阶、数量。
- 直接发放：可信业务直接提供已有模板的 DefinitionId、Grade、Count，跳过来源节点与奖励池。条目不是新的装备定义，不保存临时模板，不发布配置。

`EraRewardEquipmentGenerator` 统一将确定条目生成护甲属性或武器改装候选。地面与背包入口都使用它，装备和掉落 ID 由后端生成。模板必须存在，武器模板须允许生成；每次每人最多 120 件。

## 配置来源

`POST /api/era/worlds/{worldInstanceId}/rewards/ground` 保留正常房主入口，支持 Monster = 3、Chest = 4、Event = 5。客户端只提交来源身份、触发次数、奖励节点、原始落点和世界授权，不能指定奖励内容。后端按配置为有效参与者各自产生私人掉落，空奖也保存回执。Task 仍由可信任务业务核实完成条件。

配置发布继续使用内部 `PublishEraRewardConfigurationCommand`；配置管理 HTTP／Web 页面尚未接入。已有事件配置可继续使用，无须为直接发放额外建立必出节点或单项武器池。

## 直接地面奖励

`POST /api/era/worlds/{worldInstanceId}/rewards/ground/grant` 接收 `GrantEraGroundRewardCommand`：

- WorldInstanceId、RequestId、MemberId、AuthorityEpoch：世界与当前房主身份，RequestId 在重试时保持不变。
- CharacterId：本次领取角色，界面填写当前角色，重试和房主迁移均保持原值；须为世界内有效参与角色。
- Entries：已有模板的 DefinitionId、Grade、Count；默认普通、1 件，可提供多项。
- Placement：触发时捕获的落点与朝向。

接口沿用控制器已有 Security 权限机制，不标记 SkipPermissionCheck，也不在 Service 判断管理员。普通配置掉落入口不能提交直接条目。直接奖励给请求中固定的角色生成私人掉落；不自动给其他队员各复制一份。继续要求有效、就绪的世界及当前房主授权。

两种地面入口共用锁顺序、事件防重、资产写入、分享资格和成功回执。直接奖励记为 Internal，来源实例使用 RequestId；来源定义和节点留空。ConfigurationVersion 为 0 表示没有读取奖励池配置，ManifestVersion 仍记录实际装备目录。奖励配置缺失不影响直接发放。

相同请求和内容返回历史回执；同一请求更换条目或落点返回冲突。成功后拾取、销毁、配置改变或响应丢失，不会重抽或复活原掉落。失败事务不留下部分资产。

## 背包奖励

可信后端业务的 `PrepareEraInventoryRewardCommand` 可直接传 Entries；不传则继续查配置。两种输入均在准备阶段固定随机结果和装备 ID，再由原 Grant 命令检查容量并落库。满包重试保留已生成结果，不能将准备与发放合成一次可能重新抽取的调用。

## 游戏管理员入口

菜单为“管理员 → 装备生成 → 奖励项配置”。只对后端返回有效 SuperAdmin 角色的账号显示相关按钮，失去角色时退出管理页面。配置页查询装备目录，选择模板、品阶、数量，支持多条奖励项；在存活角色附近捕获落点后记录一次直接奖励。

继续使用 RewardEventSession 的复制、排队、重试、迁移恢复和掉落刷新。账本固定条目和落点，关闭面板不取消后端结果确认。新房主若要重试直接奖励，也须通过直接发放接口的权限检查；正常配置事件仍按原权限流程处理。没有自动接入怪物死亡、开箱或世界事件完成触发点。

`rifle_test_001` 是本地模型表现键，不是模板 Guid；配置页展示模板名称并提交模板 ID。

本批未编译、运行游戏或执行数据库测试。补充测试源码覆盖缺少奖励配置时的直接发放、武器／护甲混合条目、仅当前角色领取、拾取后重放、修改内容冲突、整批回滚及背包固定计划。未操作正式资产。
