# 奖励池与内部背包发放

更新日期：2026-10-21。源码已添加，未编译、运行测试或执行 Script0033；没有新增 HTTP 接口。

## 来源与奖励池

用户确认来源包括任务奖励、杀敌概率奖励、开箱奖励，并要求奖励池可配置。来源和发放方式分别配置，杀敌或开箱也可以配置直接进背包，不按来源硬编码禁止。

`EraRewardRules` 保存 `SchemaVersion = 1`、`Nodes` 和 `Pools`。奖励配置独立保存于 `era_reward_configuration` 固定行 `40000000-0000-0000-0000-000000000001`，初始版本 1、空节点和空池，不给现有玩家补发装备。

| 来源节点字段 | 含义 |
| --- | --- |
| `SourceType` | Internal = 1、Task = 2、Monster = 3、Chest = 4；枚举不表示业务入口已接入 |
| `SourceDefinitionId`、`RewardNodeId` | 来源定义及其奖励节点，区分大小写 |
| `PoolId` | 引用可复用的奖励池 |
| `ChanceBasisPoints` | 每名领取人每次事件独立判定的触发概率，范围 0～10000；0 必不触发，10000 必触发 |
| `Rolls` | 触发后有放回抽取次数；同一项可以重复抽中 |
| `Delivery` | Inventory = 1、Ground = 2；本批只实现 Inventory，配置 Ground 时不创建背包事件 |

池包含稳定 `Id` 及多个 `Entries`。每项配置 `DefinitionId`（Guid）、`Grade`、`Count`、`Weight`：每次按正整数权重选择一项，再产生该项数量的装备。没有写死杀敌概率、正式物品或品阶分布。

例如可让任务节点与宝箱节点共用一个池，任务节点配置 10000、杀敌节点配置较低概率，宝箱再按设计配置概率及次数；这些都是配置能力，不代表已发布具体游戏数值。不同玩家独立抽取，但属于同一批事务。

内部 `PublishEraRewardConfigurationCommand` 接收完整规则及 `ExpectedVersion`，校验池、来源节点、枚举、概率、权重、数量及引用，排他锁定配置行后版本加一。旧版本发布返回 `era.reward_configuration_version_conflict`，不覆盖新配置。该命令没有管理 HTTP 路由，后续管理入口必须接入既有管理权限；当前也没有奖励池编辑 UI。

装备目录仍是独立配置。接受事件时锁定奖励配置和装备目录，确认所选池中的装备定义可用；背包来源配置应保证任何抽取组合在空背包中可装入，即最大可能总数量不超过共享背包的 120 件，不限制单一装备类型或适用部位的数量。发布后的配置若引用尚不存在的装备定义，会在接受事件时明确拒绝，不抽出缺定义装备。

## 两步事务

这批是供可信后端业务调用的能力，三个命令及响应沿用项目结构放在 `Void.Bot.Message/Commands/ERA`，由 Core 中的 Handler／Service 实现；没有对应 HTTP 路由。任务系统未来先确认任务完成及领取资格，怪物和宝箱入口未来先确认世界、当前房主、代次、来源身份及领取人，再接相应流程；不能把客户端任意参数直接转成内部命令。

类型归属统一为：配置模型、领取人和发放回执放在 `Void.Bot.Message/Dto/ERA`；奖励服务放在 `Void.Bot.Core/Services/ERA/Reward`，内部计划及其明细放在该模块的 `Models` 子目录；数据库实体放在 `Void.Bot.Core/Domain/ERA`。每个内部数据类型独立文件。类名、属性和 JSON 字段保持原样，不变更数据库或缓存格式。

1. 单独通过 Mediator 提交 `PrepareEraInventoryRewardCommand`，保存固定事件计划。
2. 第一步提交成功后，再用独立命令事务提交 `GrantEraInventoryRewardCommand`，整批写入背包。

第一步的业务唯一键为 `ScopeId + SourceType + SourceInstanceId + TriggerIndex + RewardNodeId`。`ScopeId` 由接入业务分配且跨重试稳定；当前不是世界 ID 或世界奖励授权接口，地面流程以后须使用真正 WorldInstanceId 及世界权限屏障，不能直接复用内部调用来跳过校验。

`SourceDefinitionId` 和排序后的领取人／角色名单属于必须一致的事件内容，不加入唯一键。RequestId 在 ScopeId 内唯一，同请求改参数拒绝；新 RequestId 指向同事件时登记请求别名并返回原 EventId，定义或名单变化同样拒绝。领取人必须各不重复，角色须归属相应玩家且未禁用。

人数上限由队伍服务管理，奖励服务不重复读取网络配置或设置 4／16 人上限。世界奖励从当前队伍和有效世界参与者中确定实际名单；内部背包能力不绑定队伍，由可信调用业务提供已确认的领取人，只校验非空、身份、去重及角色归属等业务条件。每角色所有类别共享 120 件背包容量，已穿装备不计入，不按部位设置独立上限。历史事件和计划保留原名单，不以当前队伍或配置重新筛选。新增 5／16 人两个内部名单场景验证其不依赖网络人数配置，测试未执行。

首次接受时保存奖励配置版本、目录版本、来源节点及池完整快照、固定领取人、装备 ID、品阶、生成规则版本及六维结果。此时不创建正式装备或成功回执。触发概率未命中也保存空结果，不能靠重复提交再抽奖。配置、名单后续变化不修改原计划。

第二步只接收 EventId，不接收奖励参数，读取原计划，不再读取当前配置或调用随机生成器。锁顺序为奖励作用域 → 事件 → 按固定顺序锁所有玩家 → 所有角色 → 背包实例。内部命令不预加载当前用户玩家锁；必须从独立 Mediator 事务调用，不嵌入已取得玩家或角色锁的外层命令。

整批校验全部角色的共享背包总容量，再同时保存装备、护甲属性、每玩家发放回执、多装备关联、事件成功结果及角色 EquipmentVersion。任一角色剩余总容量不足则整批拒绝，无正式装备或成功回执；先前独立提交的计划保留，整理背包后重试原结果。保存异常交由工作单元回滚全部正式写入。

有装备到账的角色 EquipmentVersion 只增加一次，普通角色 Version 不变。空奖会保存成功的空回执，不增加 EquipmentVersion。装备正式 CreatedAt 使用成功发放时间，内部背包方式不创建地面或分享记录，不赋予分享资格。

成功后重试返回 `IsReplay = true` 的原回执。回执保存各角色前后 EquipmentVersion 及固定装备 ID，只表示历史发放成功；装备后来被穿上、转移或销毁，不据此恢复位置、归属或资产。

## 数据与测试

Script0033 新建配置、作用域、事件、请求别名、玩家发放回执及装备关联表，既有迁移不改动。数据库唯一约束覆盖业务事件、作用域内 RequestId、事件内每玩家奖励份额和装备对应的首次发放关联。角色归属复合外键及历史关系均禁止级联删除；不提升现有缓存版本。

本批新增 17 个集成测试场景（14 个 Fact 与一个含 3 组数据的 Theory），统一放在 `EraIntegrationFixture`，分类 `ERAIntegration`／`ERARewardIntegration`：

| 文件 | 测试范围 |
| --- | --- |
| `EraIntegrationFixture.Rewards.cs` | 整批多玩家及多件资产、六维保存、请求别名及冲突、满包保留计划、配置升级后重试、历史销毁后重放、空奖、三种来源按配置直发、地面方式明确拒绝、真实 SQL 保存失败回滚、配置发布版本冲突、领取归属与禁用检查 |
| `EraIntegrationFixture.RewardConcurrency.cs` | 同业务事件的不同请求并发准备、同计划并发发放、不同作用域竞争最后一格 |
| `EraIntegrationFixture.RewardConstraints.cs` | 真实数据库业务事件唯一键、玩家份额唯一键及跨作用域请求外键约束 |

使用真实 Mediator、EF、MySQL 和工作单元，每个请求／断言独立作用域；并发通过 SQL 信号协调，不靠固定延时。保存失败在真实 MySQL 的发放关联插入处注入 SIGNAL，再查询回滚结果；不替换业务服务或使用内存数据库。另有 `EraRewardPoolFixture` 的 13 个单元测试场景，验证概率边界、权重区间、有放回抽取及非法配置。

本批静态检查仅包含语法、源码、SQL 映射与差异检查，不等于测试通过。既有集成基类会执行 DbUp 和清理测试库，本批未实例化或运行它。
