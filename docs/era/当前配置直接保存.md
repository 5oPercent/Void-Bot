# 当前配置直接保存

更新：2026-11-04。开发阶段采用保存即生效，不维护配置的草稿、发布版本、历史、回滚或版本缓存。此前“按类别独立发布＋运行版本清单”的方案取消。

## 业务存储

| 数据类别 | 当前存储 |
| --- | --- |
| 敌人 | `era_enemy_definition` |
| 效果 | `era_effect_definition` |
| 谐振技能 | `era_skill_definition` |
| 晶格 | `era_lattice_definition` |
| 种族、阵营及关系规则 | `era_combat_relation_configuration` |
| 技能禁用标识 | `era_skill_definition.is_disabled`，默认 `false` |
| 效果禁用标识 | `era_effect_definition.is_disabled`，默认 `false` |
| 武器框架、模板、改装及槽位 | 已有 `era_weapon_*` 关系表 |
| 护甲模板、改装及槽位 | 已有 `era_armor_*` 关系表 |
| 奖励节点、奖励池 | `era_reward_configuration` 的当前规则 |
| 全局参数 | `era_configuration` 的当前配置项 |

敌人、效果、技能和晶格分别保存独立对象 JSON；共用 C# 接口只减少 CRUD 重复，不对应共用定义表。`era_data_edit_state` 只保存读取一致性和编辑并发状态，不保存业务定义。种族阵营 JSON 不存入技能表。`era_ability_settings` 已移除；技能、效果禁用标识分别保存于各自表的独立列，定义 JSON 不重复保存；晶格不增加禁用配置。

查询目录时从各表临时组合响应，不持久化第二份整包，也不按旧版本读取。武器、护甲继续直接修改自己的关系表，批量替换接口改称保存。

## 服务边界

| 职责 | 业务服务 | 数据访问范围 |
| --- | --- | --- |
| 晶格配置 | `IEraLatticeService` | `IEraLatticeDataProvider` → 晶格表 |
| 技能配置 | `IEraResonanceService` | `IEraResonanceDataProvider` → 技能表，包含禁用列 |
| 效果配置 | `IEraEffectService` | `IEraEffectDataProvider` → 效果表，包含禁用列 |
| 敌人配置 | `IEraEnemyService` | `IEraEnemyDataProvider` → 敌人表 |
| 种族、阵营及关系 | `IEraCombatRelationService` | `IEraCombatRelationDataProvider` → 关系表 |
| 角色技能学习、四槽配装 | `IEraAbilityProfileService` | `IEraAbilityProfileDataProvider` → 角色学习与配装表 |
| 当前能力目录、导出、引用查询 | `IEraAbilityCatalogQueryService` | 只读聚合各类别数据，不提供保存和删除入口 |

各类别列表与详情只读取自己的业务表。保存、删除先锁定当前编辑状态，再通过只读目录校验跨类别引用，最后仅修改本类别数据；保留原有事务提交、过期编辑保护和同 Key 跨类别隔离。`EraDefinitionService<TRecord,TDefinition>` 和对应数据访问基类只复用通用校验、分页与单表操作，不进行按类别分发的聚合写入。

[目录查询实现](../../src/Void.Bot.Core/Services/ERA/Configuration/EraAbilityCatalogQueryService.cs) 顺序读取各独立访问器，读取前后核对修订号，变化时重试；不保存组合结果。角色业务通过这个查询边界获取当前规则，不依赖技能配置写入服务。联机主机读取成员配装沿用 `IEraWorldAbilityService`，归入角色能力模块。

本轮仅调整后端职责与调用依赖，保留现有 HTTP 路由、消息契约和客户端目录字段，不增加数据库迁移或提升缓存、网络协议版本。

## 保存与删除

- 新建使用 `expectedVersion=0`，修改和删除携带读取到的编辑令牌。此令牌只防止过期页面覆盖数据，没有历史查询或发布操作。
- 保存先校验当前定义及引用，成功后在同一事务中更新对应业务表；新读取立即取得新值。
- 删除直接移除当前定义；仍被技能、晶格、敌人或设置引用的对象不能删除。删除后重新创建相同 Key 时使用新的编辑令牌，旧页面不能覆盖新对象。
- 编辑失败时不能改动已跟踪的业务实体。对象预算为每类别最多 10,000 项、组合配置最多 1 MiB；没有删除标记或历史记录占用预算。
- `SchemaVersion` 表示数据结构，装备及奖励的来源编号、玩家并发令牌与 RPC 协议标识保持各自职责，不视为配置版本缓存。

## Web 与客户端

Web 移除“数据发布／版本管理”、发布预检、历史恢复及发布重试工作流。各配置页直接保存、删除。“能力设置”页面已删除，禁用状态在每条技能或效果的编辑页维护，列表右侧显示禁用标识。效果禁用保留引用，客户端不再施加该效果。通用战术池已取消，客户端候选只展示当前晶格各槽位配置的技能。旧发布请求的 `sessionStorage` 记录在进入后台后清理，配置接口使用 `no-store` 请求。

客户端能力配置 DTO 和编译目录不再带发布 `Version`。读取后端当前目录时明确禁用 HTTP 缓存，每次新任务读取当前配置。角色配装、装备操作和奖励事件仍保留业务并发及防重信息。

联机对局快照携带本局实际使用的数据，重连和主机迁移继续按内容校验，避免主客机结算不同。它不提供历史配置查询；保存后台配置不会自动热替换正在执行的技能或 BUFF。后续读取／新任务使用最新数据。

任务快照的配置结构移除了发布版本字段，因此 RPC 协议由 26 调整为 27；未新增磁盘配置缓存。

## 数据库迁移

按顺序执行 `Script0048` 至 `Script0052`；DbUp 已登记的脚本不重复执行。本次检查针对种族阵营、武器护甲、晶格、技能和效果已有数据的情况，敌人无旧业务数据，不增加敌人旧字段转换。

1. `Script0048` 仅清理已退役的编辑器元数据；非空旧结构技能不通过修改 SchemaVersion 冒充转换成功。
2. [Script0049_remove_buff_presentation_key.sql](../../src/Void.Bot.Core/Dbup/Scripts/Script0049_remove_buff_presentation_key.sql) 只移除效果的退役表现字段。保留效果顺序及其它字段，重组前后核对长度与数量，避免字符串聚合截断；重复执行不会再次增加草稿令牌。
3. [Script0050_current_era_configuration.sql](../../src/Void.Bot.Core/Dbup/Scripts/Script0050_current_era_configuration.sql) 先检查来源行、JSON、类别、身份及禁用引用。已初始化编辑区是完整的最新保存快照，只迁移非删除定义；不补回旧发布中已被删除的对象。未初始化时从旧当前整包提取定义，兼容根集合属性的两种大小写写法，冲突则中止。
4. 种族阵营及关系规则迁往独立关系配置表。已初始化编辑区缺少该设置时回退原有整包；显式保存的空集合仍保留为空。技能禁用选择采用相同的缺失回退规则。
5. 各类别暂存后写入独立业务表，核对记录数量、Key、JSON 内容、编辑令牌和审计字段；全部一致后才删除旧整包、草稿与发布表。旧历史不迁移，通用战术池按已确认需求取消，晶格自己配置的四个技能池完整保留。
6. [Script0051_skill_disabled_state.sql](../../src/Void.Bot.Core/Dbup/Scripts/Script0051_skill_disabled_state.sql) 将技能禁用状态迁入技能表独立列，再删除过渡设置表及已取消菜单。原定义存在独立布尔标记时优先采用，否则使用旧禁用列表。
7. [Script0052_effect_disabled_state.sql](../../src/Void.Bot.Core/Dbup/Scripts/Script0052_effect_disabled_state.sql) 将原有效果禁用标记迁入效果列；无标记的效果默认启用。两项迁移均验证其它定义内容未改变。

武器、护甲、框架、改装、槽位、装备元数据、玩家装备与配装、奖励事件均不被这些脚本改写。特别是 `era_equipment_configuration.payload` 保持原值，不再清空。

迁移保留每类 10,000 项的现有应用边界，现有数据已确认未超出。脚本不使用存储函数、`DELIMITER`、`JSON_TABLE` 或窗口 JSON 聚合，以符合项目约定的 MySQL 8.0.3 功能范围；实际回归运行环境为本机 `mysql:8.0` 镜像（8.0.46），未在 8.0.3 二进制上运行。

MySQL 的 DDL 会隐式提交，因此不能把 DbUp 的事务视为整段迁移可回滚的保证。这里采用删除来源前逐项核对的方式；校验失败会报错中止，不继续清理来源表。失败后需先检查已创建的目标表及 DbUp 登记状态再重试。[MySQL 官方说明](https://dev.mysql.com/doc/refman/8.0/en/implicit-commit.html)

### 隔离迁移验证

回归脚本：[test_current_era_configuration.py](../../tests/migrations/test_current_era_configuration.py)。只使用 Python 标准库，不编译项目。必须指定带 `codex.task=era-migration-audit` 标签、无网络且无端口映射的临时 MySQL 容器；每例创建独立随机测试库并清理。

```text
python tests/migrations/test_current_era_configuration.py --container <临时容器名>
```

验证覆盖旧发布与完整草稿来源、缺失设置回退、显式空设置和删除、种族阵营关系方向、晶格技能池、技能效果参数及禁用标记、Unicode、超出 JavaScript 安全整数的数值、长效果数组及顺序、异常来源中止。装备等受保护表使用代表性哨兵行比较，并结合脚本写入目标检查；不等同于真实数据库全量比对。

本轮未连接或执行实际业务数据库迁移；目标库迁移后的各表记录核对仍保留为下方 TODO。
